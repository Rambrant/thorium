# ui/ -- the bench console

A desktop window over the same run `run_scripts` performs, for an operator who
is standing at a rig rather than sitting at a terminal. Everything the CLI can
do, it can do.

It is a **separate program, in a separate build tree, built by a different
compiler**, and it links nothing in `framework/`. That is the first and largest
decision here, so it goes first.

---

## 1. Why it is a separate process

Three reasons, in descending order of how hard they are to argue with.

**The framework's build is not a place to put a GUI toolkit.** The top-level
`CMakeLists.txt` refuses to configure on anything but GCC 16 and passes
`-freflection -fcontracts -Wall -Wextra -Wpedantic -Werror` to every translation
unit in the tree. Those flags are not decoration -- reflection is what makes
`cli.hpp` and the wiring-coverage checks possible, and `-Werror` is why a warning
has never been ignored here. A toolkit dragged inside that fence has to survive
all of it, on three platforms, forever. On macOS it is worse than inconvenient:
Homebrew's GCC compiles against libstdc++ while every prebuilt toolkit on the
machine is built against libc++, and two C++ runtimes in one process is a class
of bug nobody should spend an afternoon on. Outside the fence, the UI is
compiled by whatever compiler the platform hands it and the question never
arises.

**The binary is already an interface, and it is already tested as one.**
`acceptance/test_acceptance.cpp` drives `run_scripts` as a subprocess and
asserts on its stdout, its exit code and its log files -- "the binary's stdout
and its log files are the entire interface under test", as
`framework/runner/CMakeLists.txt` puts it. The UI is a second consumer of that
same interface, not a new one. `cmake/GenerateManifest.cmake` had already gone
further and written `manifest.json` next to each installed binary so that a
supervising process could discover suites without parsing C++.

**A run that crashes must still be safe-able.** `main.cpp` explains why `--safe`
exists at all: *"The rig console supervises a run as a child process, and on an
abnormal exit it cannot reach into the dead process's `hal::fabric` to open
anything -- so it re-invokes this same binary with `--safe`."* That paragraph
describes this program. An in-process UI would be the dead process.

### What the boundary costs, and the one thing that pays for it

It costs a wire format, and a wire format is a second place facts can be
written down. This tree's whole argument is that a fact written down twice will
eventually be written down differently. So the boundary is only honest if
nothing that crosses it is *restated* on the far side.

Two things cross, and neither is restated:

| The UI needs to know | Where it comes from | Why it cannot drift |
|---|---|---|
| what the flags are | `run_scripts --describe-options` | generated by `cli::optionsModel` from the same annotations `--help` is generated from |
| what the run is doing | `run_scripts --events=-` | `core::EventSink`, a third rendering of the one journal |
| what tests exist | `run_scripts --list-tests` | the catalog itself, and already what `manifest.json` is built from |
| which tolerance variants exist | `manifest.json` | written at install time by asking the installed binary |

There is no list of flags in `ui/`. There is no list of tests in `ui/`. A flag
added to `Options` in `main.cpp` appears in this window with no edit here at
all, which is the same promise `--help` makes and for the same reason.

`cli.hpp`'s opening comment says it stays in `framework/runner/src/` because
"main.cpp is its only consumer" and that a second consumer would be the moment to
promote it to a public header. The UI is exactly the consumer that would have
forced that move -- and does not, because it never includes the file. What
crosses the boundary is data, not a header. That is the argument for the process
split stated in one sentence.

## 2. What the UI adds, and what it deliberately does not

It adds the three things a terminal cannot give an operator at a bench:

- **A catalog you pick from** rather than a `--select=` list you type. Test ids
  come from `--list-tests`, so a mistyped one is not possible -- the class of
  error `unmatchedSelection()` exists to catch cannot be made here.
- **A run you watch.** Verdicts land as they happen, in the catalog's own shape,
  because the event stream carries the boundaries as well as the readings.
- **A rig you can drop at any moment.** One button, always live, including while
  a run is in progress and including after one has died.

It deliberately does **not** add: a way to edit criteria, a way to author a
stimulus file, a second opinion about whether a check passed, or any state of
its own about a run. The window is a view and a launcher. Every verdict in it
came out of the event stream with `passed` already decided, and the authoritative
record is still the RTF and the SARIF file the run wrote. If the window and the
log ever disagree, the log is right and this is a bug.

The last one is worth being explicit about, because it is the temptation the
whole design has to resist: a UI that recomputed a pass/fail, or tallied its own
totals from the events, would be a second implementation of `Journal::endTest`
in another language. It tallies nothing. `testEnd` carries the verdict and
`runEnd` carries the run's.

## 3. The shape of the window

```
+----------------------------------------------------------------------+
| Suite: [ DevBench -- dev-desk          v ]   DUT serial: [ SN-...   ] |
| Criteria: [ production v ]                   Operator:    [ ...     ] |
+---------------------------+------------------------------------------+
| Tests                     | Run                                       |
|                           |                                           |
| [x] BenchSanity           |  BenchSanity                              |
|   [x] DmmSelfCheck        |    DmmSelfCheck                           |
| [ ] OutputVoltage         |      Dmm1.Voltage        5.012 V          |
|   [ ] SupplyRail          |      FS_Supply_5V0       PASS  = 5 V +-50m|
|   [ ] AcDropout           |      ...                                  |
|                           |                                           |
| [ Options... ]            |                                           |
+---------------------------+------------------------------------------+
| [ Run ] [ Stop ]   [ Safe the rig ]            3/9 -- 1 failed        |
+----------------------------------------------------------------------+
```

Two panes and a bar. The left is the catalog, the right is the run, the bottom
is what you press. Nothing in the layout is clever, on purpose: the operator
looking at it has their hands on a fixture.

**"Options..." is a generated dialog.** Every flag `--describe-options` reports,
except the ones marked `query` and the five the window already owns, gets a
control chosen by its `kind`: a `switch`
is a checkbox (checked to begin with if it `clears`, since a `--no-...` flag
exists to turn something off), a `number` is a spinner that will not go to zero
if it is `positive`, a `list` is a field, and everything else is a field with
its `placeholder` as the hint. The `help` string is the tooltip. That is the
entire mapping, and it is why the dialog needs no maintenance.

**Five flags are left out because the window drives them itself** -- `--select`
is the test tree, `--criteria` the picker, `--dut-serial` and `--operator` the
header fields, `--safe` the button. That list of names lives in `ui/`, which
everything else here goes to some length to avoid, and the distinction is the
argument: it does not say what the flags *are*, it says which of them this
window surfaces specially, which is a fact about the window and lives nowhere
else. Without it an operator can set a flag twice from two controls and see no
sign of the contradiction. The window checks every name in it against the model
at load time, so a flag renamed in `run_scripts` is reported rather than
quietly reappearing in two places.

**The dialog starts empty and stays empty.** A control the operator has not
touched contributes no flag to the command line. This is not laziness about
defaults -- reflection cannot read a member's default initialiser (`cli.hpp`
says so where it runs into the same wall), and the behaviour that falls out is
the behaviour we want anyway. `main.cpp` twice depends on telling *"the caller
said nothing"* from *"the caller named the default"*: `--criteria=` unset means
the build's variant rather than a name, and `--repeat` unset with
`--until-failure` means "keep going" rather than "once". A dialog that helpfully
pre-filled every default and always passed it would quietly destroy both.

## 4. How a run happens

```
run_scripts --quiet --no-color --events=-  --select=...  [flags from the dialog]
```

`--quiet` is not optional and the runner enforces it: `--events=-` puts JSON on
stdout, which is where the console view writes its coloured prose, and a
supervisor that cannot tell a malformed stream from a finished one has nothing.
So `parseOptions` refuses the combination rather than silently suppressing the
console -- a runner that decided it knew better than the caller would be the
wrong kind of helpful.

The UI reads the child's stdout a line at a time. Each line is one JSON object
with a `kind`, and the kinds are the journal's own hooks --
`runStart/groupStart/testStart/phaseStart/event/testEnd/groupEnd/runEnd`. The
format is documented where it is produced, in
[`core/journal/event_sink.hpp`](../framework/core/include/core/journal/event_sink.hpp),
including why it is line-delimited rather than a document: a truncated stream is
a whole number of valid events, where a truncated SARIF file is nothing at all.
That matters here more than anywhere, because the process being watched is one
whose death is a case this window has to handle well.

**Logs still go where logs go.** The UI passes no `--no-logs`. A run started
from this window leaves the same RTF and SARIF in the same place as one started
from a terminal, because a run's record must not depend on how it was launched.

### When the run dies

Four outcomes, and the UI tells them apart because the stream does:

| | |
|---|---|
| `runEnd` arrived, exit 0 | passed |
| `runEnd` arrived, exit non-zero | ran, something failed -- the verdict is in the stream |
| no `runStart` at all | **never started** -- the reason is on stderr, nothing was energised |
| `runStart` but no `runEnd` | **crashed**, and the rig's state is unknown |

The last two look alike from outside -- both exit non-zero with no result -- and
only the stream tells them apart. `run_scripts` refuses before
`journal().begin()` for everything it can know up front: contradictory flags, an
unwritable log, a recording with no rows for the selection, a preflight that
could not reach an instrument. None of those touches a relay, so there is
nothing to safe and nothing unknown about the rig; what the operator needs is
the sentence `run_scripts` already wrote to stderr, which the window shows them.

Conflating the two is not harmless, and it is not hypothetical -- the first
version did, and a desk with no meter plugged in produced *"the rig's state is
unknown, do not approach the fixture"* for a run that had not energised
anything.

The last is the one that matters. The window says so plainly, and re-invokes
`run_scripts --safe` -- the same binary, built against this rig's exact
instrument list, which is why `main.cpp` put the mode there rather than in a
tool of its own. It cannot be wrong about what there is to safe.

The "Safe the rig" button does the same thing on demand, and is enabled at all
times including during a run. It is the one control in the window that is never
greyed out.

## 5. Why wxWidgets

Native controls on all three platforms from one source, a licence with no
relicensing obligation if this ever ships inside a product, and a CMake build
that `FetchContent` can drive when a system copy is not there. A tree view with
checkboxes, a styled text control, a form, and native file dialogs are all
stock -- which is the whole requirement, since section 3 asks for nothing
unusual.

The alternatives and why not: **Qt** is the better toolkit and was the near
miss, but LGPL dynamic linking is a conversation rather than a non-issue, and it
is a much heavier thing to require on three bench PCs. **Dear ImGui** would have
been the right answer for a developer's debug window and the wrong one for a
console an operator uses all shift -- immediate mode, weak accessibility, no
native dialogs. **A browser front-end** remains the right answer for the
*lab-wide* view that `manifest.json` was written for; it is a different program
from this one and does not replace it.

## 6. Building it

The UI is **not** part of the framework build and is not reachable from its
presets. It is configured separately, against an install prefix where one or
more suites have been installed:

```bash
cmake -S ui -B build/ui -DTHORIUM_SUITE_PREFIX=/opt/thorium
cmake --build build/ui
```

`THORIUM_SUITE_PREFIX` is a default, not a binding -- the window's suite picker
can be pointed anywhere, and a prefix holding several installed suites shows
several entries. Each is discovered the way `GenerateManifest.cmake` intended:
find a `manifest.json`, read the binary beside it.

wxWidgets is found with `find_package(wxWidgets)` and fetched if that fails.
On a developer machine:

```bash
brew install wxwidgets           # macOS
sudo apt install libwxgtk3.2-dev # Debian/Ubuntu
vcpkg install wxwidgets          # Windows
```

Built and run against wxWidgets 3.3.3.

### The tests, and why there are two

```bash
cmake -S ui -B build/ui -DTHORIUM_UI_TEST_BINARY=$PWD/build/dev/bin/run_scripts
cmake --build build/ui
ctest --test-dir build/ui
```

Both need a built `run_scripts` to drive, and neither uses a fixture where it
could use the real thing. A test asserting on a hand-copied event schema keeps
passing after the schema changes, and the schema is the entire contract between
these two programs.

`ui_protocol` links no toolkit at all — it is the reader and the command
builder, checked against real `--describe-options`, `--list-tests` and
`--events=-` output. `ui_process` links wxWidgets but builds a console binary,
because everything `ChildProcess` touches is wxBase: it covers the part of the
window that cannot be checked by pressing Run, which is what happens when a run
*doesn't* finish. Set `-DTHORIUM_UI_FETCH_WX=OFF` on a machine with no toolkit
and `ui_protocol` still builds and runs — that is the check worth having on
every commit, and it needs no display.

### Three things the build taught, which are now comments in the code

- **`wxExecute` has no capturing overload that takes an argv array.** The
  output-capturing forms take one command *string*, which a shell re-splits —
  and this program is handed paths it did not choose. That is why asking a
  binary about itself is asynchronous like a run rather than a blocking call:
  there was no synchronous form that could be used safely.
- **`wxInputStream::Read` blocks trying to fill its buffer.** Against a run's
  stdout, which stays open and idle between readings, that would have frozen
  the window for as long as the rig took to settle. The pipe is drained a byte
  at a time behind `IsInputAvailable()`, which is the only form that cannot
  wait.
- **A flag that means one thing for a run means nothing for a query.**
  `ChildProcess` reports "crashed" when no `runEnd` arrived -- and a `--safe`
  invocation asks for no event stream, so there is no `runEnd` for its absence
  to mean anything. Testing that flag in the safing handler made every
  *successful* safing report "SAFING FAILED -- do not approach the fixture". It
  is now narrowed where the call is configured rather than left to each handler
  to remember.
- **A handler must not destroy its own `ChildProcess`.** Chaining one child to
  the next by assigning the owning pointer from inside a callback destroys the
  lambda mid-call. It does not crash — it silently skips the step, which is how
  it survived the first round of testing. The chain goes through
  `wxEvtHandler::CallAfter`.

## 7. What this does to the framework

Deliberately little. Three additions, each of which stands on its own:

| Addition | Where | Would it exist without the UI? |
|---|---|---|
| `core::EventSink` | [`event_sink.hpp`](../framework/core/include/core/journal/event_sink.hpp) | yes -- `journal.hpp` had already argued for a live stream as the example of what the fan-out design buys |
| `cli::Query` + `cli::optionsModel` + `--describe-options` | `framework/runner/src/cli.hpp` | no. This one is for the UI, and it is the price of not restating the flags |
| `core::jsonEscape` | [`json.hpp`](../framework/core/include/core/journal/json.hpp) | it is the escaper `SarifSink` already had, moved so the second JSON stream could not grow a second copy |

No verb changed. No script changed. No sink changed. The event stream exists
because `IJournalSink` was designed for exactly this and had been waiting for
somebody to try it.

## 8. Linux

The framework's presets were macOS and Windows only. Adding a third host was
required by "portable between Windows, Linux and macOS" and is otherwise
unremarkable -- `linux-debug`, `linux-release`, `linux-dev`, conditioned on
`${hostSystemName}` the same way the other two are, naming `g++-16` on `PATH`
rather than an absolute path, since no distribution agrees on where it lives.

Nothing in the framework was platform-specific to begin with; the presets were
simply the only two anyone had needed.
