The problem

Four ways a test suite lies to you

  • A mistyped test point measures the wrong pin — and passes
  • A criterion compared against the wrong unit — and passes
  • A relay path nobody wired up — throws three hours into a soak test
  • A tolerance table edited for one variant, not the others
  • Every one of these is a static fact.
  • None of them needs a running rig to discover.

The payoff

Two checks worth a closer look

  • Wiring coverage. One test file has no assertions at all — the point is that it compiles. It walks every declared test point and demands a matching wiring entry. Forget one and the build stops.
  • Tolerance variants. Production, stress-chamber and aged-equipment limits are three tables. A value unchanged from production is written once and referenced — so it cannot drift, and a typo in the reference will not compile.

Honestly

Pros and cons

  • Strengths
  • Whole classes of mistake cannot reach the bench
  • Scripts trace straight to the spec
  • Operator view and machine record cannot disagree
  • Scripts testable with no hardware
  • One tolerance value, three tables
  • Reusable across benches
  • Costs and risks
  • Experimental C++26; GCC 16 only
  • New scripts need a developer, not a spreadsheet
  • Wiring changes mean a rebuild
  • Few engineers have used reflection
  • Instrument drivers still simulated
  • Template errors can be verbose
